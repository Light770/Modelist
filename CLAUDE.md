## Commands

Run from the repo root unless noted:

```sh
npm run build:wasm      # wasm-pack → apps/web/src/wasm-pkg (rerun after ANY Rust change used by the web app)
npm run dev             # Astro dev server (needs wasm-pkg built first)
npm run build           # build:wasm + astro build
npm run test:rust       # cargo test --workspace (sim3d drape tests take ~1 min)
cargo test -p modelist-core              # fast loop for 2D kernel work
cd apps/web && npm run test:unit         # esbuild + node --test for src/lib/cad
cd apps/web && npm run check             # astro check (TS type check)
```

Before calling a change done, run the relevant Rust tests, `npm run build:wasm` if the WASM API changed, and `npm run check` if TS changed.

## How the pieces talk

- **Data flow:** the UI calls `kernelClient.ts` → `ModelistSession` methods (WASM). The kernel mutates `PatternProject`, rebuilds from the parametric op timeline, and exposes:
  - `get_ui_snapshot_json()`: the JSON `UiSnapshot` the React chrome consumes (typed in `types.ts`)
  - `get_stroke_coords()` / `get_stroke_meta()` / `get_handle_points()`: typed arrays that Viewport2D draws imperatively
  - `get_sim3d_*()`: typed arrays for the 3D viewport
- **Changing the WASM API** is a 3-place edit: `crates/modelist-wasm/src/lib.rs` → `kernelClient.ts` wrapper → `types.ts` (if the JSON shape changed). Then rebuild wasm-pkg.
- **Garments (components):** a `PatternProject` is one body (measurements, size table, grading) wearing one or more `GarmentComponent`s. Each component has its own template, ease, formula variables, fabrics, op timeline, custom pieces, 3D `layer`, `offset_2d` on the canvas, and `visible` / `visible_3d` flags. `blocks::build_project_pieces` drafts every component and returns `piece_component` (owner of each piece). Grading, nesting, POM/RUL exports and the session rebuild all go through it. The first component keeps the template's own IDs. Later ones get an `id_ns` prefix (`remap_entity_ids`) so the same template can be worn twice. The session's `project.comp()` / `comp_mut()` is the **active** garment: parameters, fabrics and the timeline apply to it. Selecting a piece activates its garment, and `insert_op` routes an op to the garment that owns its target piece. Create components with `library::new_component` / `new_project`, never by hand.
- **Parametric model:** fitted blocks (`bodice_sleeve`, `aline_skirt`, `trouser_block`) are built in `blocks.rs`; starter styles (`boxy_tee`, `wide_pleat_trouser`, `barrel_trouser`) in `library/`. Both draft from `BodyMeasurements` + `EaseTable` + variables, then the `ParametricOp` list (timeline, with rollback/suppress/reorder) is replayed. Edits should become ops, not raw geometry mutations, so they survive measurement changes.
- **Template catalog:** `library::TEMPLATE_CATALOG` is the single list of templates (name, category, measurement keys, 3D view region). WASM exposes it as `template_catalog_json()`; the template picker and inspector read it via `apps/web/src/lib/templateCatalog.ts`. Add new templates there instead of hard-coding ids in the UI. New style builders must use `library::sclamp` (never `f64::clamp` with computed bounds, which panics and traps WASM) and pass the library test-suite (`cargo test -p modelist-core library`).
- **IDs:** use `det_id("kind:name")` (UUID v5) for deterministic IDs. Never use random UUIDs for pattern entities.
- **Persistence:** projects are saved as `.modelist` containers (`modelist_core::container`), written by `save_project_container` and read by `load_project_file`. A container is a ZIP whose first entry is `mimetype` (stored), followed by `manifest.json` (format version, writer, a SHA-256 per part), `project.json` and one `components/<id>/component.json` per garment, plus an optional `thumbnails/preview.png` and `session.json` (UI state). Parts the build doesn't know are kept and written back (`container_extras`). The IndexedDB autosave stores the same bytes. "Export as JSON" writes the whole project as one document for debugging. Always read projects through `load_project_file` / `read_container` / `PatternProject::from_json`, never `serde_json::from_str`: they check `format_version` (currently 1), migrate version 0 single-garment files into one component that keeps its IDs, and refuse files from newer builds. The published contract is `docs/format/modelist-v1.schema.json`, generated from the Rust types (`#[derive(schemars::JsonSchema)]`). A test fails when the schema is stale; regenerate it with `MODELIST_UPDATE_SCHEMA=1 cargo test -p modelist-core published_schema`. Fields a build doesn't know are not preserved inside a part, only whole unknown parts.
- **Garment library:** a saved garment is a single-garment `.modelist` file (`export_component_file`) stored locally in IndexedDB (`garmentLibrary.ts`, `garment_library` store). `insert_component_file` and `duplicate_component` add garments through `library::relocate_component`. It moves every ID into a fresh namespace by drafting the template's own IDs to map drafted ones, then rewriting every UUID in the component JSON, so the garment's history keeps finding its pieces. `library::shift_component` moves it on the canvas, including custom pieces and the absolute `AddDrillHole` positions. New ops with absolute coordinates must be added to `shift_component`.

## Current state vs. spec (as of 2026-11)

The spec describes the target. These parts of the code currently differ from it, so don't assume the spec is already implemented:
- The WASM kernel runs on the **main thread** (no Web Worker yet); snapshots are JSON strings.
- 2D viewport is **Canvas2D**; 3D viewport is **WebGL2** with a **CPU XPBD** solver in Rust (no WebGPU compute yet).
- The solver runs 12 substeps per frame: anisotropic strain-based membrane (warp/weft/shear), long-range tethers sized from the mesh, per-edge and seam-line stretch limits, quadratic (Bergou) bending calibrated on the Peirce cantilever, inelastic SDF contacts with velocity-level friction, body-point vs triangle contacts. Lower-body garments get a waistline support until tacks/waistbands exist.
- **Garment layers** (one layer number per piece, 0 = next to the body; the WASM side passes each piece's component layer and qualifies fabric roles per garment with `material::garment_role`): layers are dressed inner first. `ClothSimSession::start_dressing` returns once the inner layer has draped and puts the others on during later `step()` calls, so the page doesn't freeze. `Sim3dStats.dressing_layer` / `dressing_layers` report progress, and Viewport3D re-uploads topology when `vertex_count` changes. `new_layered` is the blocking form used by tests. After an edit, the session compares per-layer fingerprints of the 3D inputs (`sim_layer_keys`: pieces, seams touching them, fabrics, body, pose). It keeps the fit when nothing changed, and otherwise calls `ClothSimSession::redress_from`, which keeps the settled layers under the first changed one and re-dresses from there. That is exact because lower layers have priority. The gentle sewing phase of a layer ends when its seams meet, or when the largest gap stops closing. A garment hidden in 3D is still simulated; only its triangles are filtered (`triangle_indices_shown`). Each pass rebuilds the scene with one more layer, keeps the lower layers where they settled, wraps the new layer around them (`arrange::InnerShell`) and sews it gently until its seams meet. Between layers, one-sided vertex-triangle contacts apply where the normals are aligned (stacked cloth), and the lower layer has priority. Where the parts sit side by side (inner sleeve against outer side panel at the armpit), they keep apart on their current side. There is still **no general cloth-to-cloth or self collision**, so the armpit region can still intersect. Tuck-in is just the layer order (`test_tuck_in_is_the_layer_order`). Dressing two tees takes about 7 s natively, against 0.6 s for one.
- Seams have no fold angle / turned / layer properties yet (see the 3D overhaul report in memory for the plan).
- Nesting (`nesting.rs`) is an in-house BLF-style implementation. `jagua-rs`/`sparrow` are **not** dependencies. Flag the MPL-2.0 license before adding them.
- Some WASM methods still address edges by `edge_idx: usize` even though the skills prefer `EdgeRef`/UUID references. Prefer UUID-based references in new code.

## Conventions to keep in mind

- All kernel math is `f64` mm; sim3d uses `f32` meters internally (convert at its boundary).
- No geometry math in TypeScript. If the UI needs a measurement or hit test, add a kernel method.
- Never render pattern geometry as React DOM/SVG during interaction. Viewport2D draws from typed arrays in rAF.
- Keep 3D lazy: nothing in `modelist-sim3d` may run unless the 3D Fit Room is open; call `dispose_sim3d` on close.
- New geometric/solver code needs unit tests + `proptest` invariants (see AGENTS.md §3 and spec §10.2).
- **Fabrics are physical:** `FabricSpec` stores N/m, µN·m, g/m², % (see `FABRIC_PROPERTIES` for keys and ranges); old 0-1 slider files are migrated by `FabricSpec::normalized()`. Never add a non-physical fabric knob; extend `FABRIC_PROPERTIES` instead. `fabric_*` formula variables are mirrors of the shell fabric and are read-only.
- **Sim changes need the drape checks:** `cargo test -p modelist-sim3d --release` runs the textile calibration tests and the drape-quality tests (poke-through, creases, waist hold per fabric). Seam gaps and strain alone do not catch crumpling.
- **All UI text goes through i18n:** `const t = useT()` and `t('key')`; add the key to `en.ts` and `fr.ts` (fr is typed, a missing key fails `npm run check`). Kernel catalog names (templates, fabric presets, measurements) are translated by id with `useCatalogT()`. Pattern data typed by users is never translated.
- Studio deep links: `/?template=<id>&mode=2d|split|3d&lang=en|fr&tab=params|materials|grading` (also under `/studio`).

## Desktop shell (Fusion-style)

The studio is a desktop application, not a web page: `body` has a 1100 px minimum width and nothing scrolls except panels. The layout follows the user's sketch (2026-11-24). From top to bottom:
- **`AppBar`**: project space button (`DataPanel`: open documents + starter library), File menu, save/undo/redo, **document tabs** (`+` opens a template in a new tab, double-click renames), **Params**, and **2D / 3D check toggles** (both on = side by side; at least one stays on). Each document has its own WASM `ModelistSession` (`openDocument` / `switchDocument` / `closeDocument` in `kernelClient.ts`), so undo history stays per tab; only the visible one keeps a 3D simulation.
- **`Toolbar`**: a **Design ▾ / Production** workspace switch, then tabs (Design: Patterning, Sewing, Styling, Rendering, Materials, Tools; Production: Grading, Output), then command groups. Commands are data (`ToolCommand` / `ToolGroup`): icon, label and description from `cmd.<id>.label|desc` or `tb.*` keys, shortcut, active/disabled state. A group label opens a menu of all its commands; hovering shows a card. While a command runs, a highlighted contextual group offers Finish / Cancel. Add new commands here, not as floating buttons on the canvas.
- **Canvas** (`<main>`): the 2D and 3D views fill it. The Browser (`LeftPanel` in a `FloatingPanel`) floats top-left. The right side is **`PropertiesPanel`**, which is contextual (progressive discovery): a page opened on purpose (`panelPage`: params, materials, grading, piece) wins, else the running command's options (`SeamCommandDialog`, or `ToolOptions` for tools in `TOOLS_WITH_OPTIONS`), else the selected piece (with a selected-edge card). With nothing to show it disappears; closing it hides it until the context changes. Tool options and prompts live in `ToolOptions.tsx` (`TOOL_PROMPTS`), not as HUDs on the canvas. Each view has a bottom-centre navigation bar; 2D "fit" centres the pattern in the area not covered by panels (`visibleInsets`).
- **`BottomBar`**: the parametric history (timeline) across the full width, then the **`CommandLine`** ("/" focuses it): fuzzy command search in the current language, `name = value` sets a measurement, ease or formula variable, and it shows the running tool's prompt. Status (messages, snap, cursor, zoom, units, 3D solver state) sits to its right.

Dropdowns use `Menu.tsx`, which renders into `<body>` through a portal: anything that must appear above the floating panels needs the same treatment, because flex items with a z-index create their own stacking context. 3D play/pause, re-drape, pose and body form live in the store (`sim3dPlaying`, `sim3dResetSeq`, `sim3dPose`, `sim3dBodyForm`); `Viewport3D` reacts to them. Astro's dev toolbar is disabled in `astro.config.mjs` because it covered the status bar.
